# 实战经验与硬门

本文件记录真实执行中暴露的问题。它不是建议，而是发布前必须检查的约束。

## 1. 先定叙事主线，再选素材

- 在状态文件记录 `content.angle`：一句话说明这条内容要打什么点，例如“学校让班级平摊滤芯费”。
- 记录 `content.must_include`：必须进入标题、图片或正文的事实。
- 记录 `content.excluded_outcomes`：本次明确不进入标题、图片、正文的后续结果，例如“已清退”“校方承担”“专项核查”。
- 标题、第一段、图片字幕、结尾问题必须围绕同一个 `content.angle`。不能标题讲分摊，图片却主要讲退款，也不能图片讲分摊，正文转向通报结果。
- 省略后续结果是编辑选择；不得篡改、反向表述或编造事实。所有进入内容的事实仍需可回溯。

检查口令：

> 标题的主语和冲突是什么？图片字幕是否逐条支持这个冲突？正文第一段是否先讲清同一个事件？

三个答案不一致时，禁止进入上传阶段。

## 2. 曝光事件优先使用“最热曝光视频”

热点事件通常有三类素材：

- `exposure`：事件第一次被曝光、传播最广的原始视频或截图视频
- `commentary`：后发的评论、解读、律师分析
- `official`：官方通报、新闻播报、处理结果

当用户要的是“自媒体热点事件叙事”时：

1. 优先选 `exposure`，不是 `official`。
2. 在站内搜索事件关键词，比较发布时间、热度、作者和时长。
3. 优先选择事件发生后 `0–24 小时` 内、热度最高、字幕最清晰的曝光视频。
4. 状态文件记录 `source.role`、`source.published_at`、`source.heat_evidence`、`source.url`。
5. 如果曝光视频只有事件过程，不要强行把它扩展成官方结论。
6. 如果用户明确要求“只描述事件”，时间点必须截止在结果段之前。

## 3. 原生字幕模式锁定后不得擅自切换

一旦用户要求或此前确定使用 `native-subtitle-quote-image` 的原生字幕模式：

- 不得为了去重改成自制信息卡。
- 不得为了排版切换到脚本字幕模式。
- 不得 OCR 后重绘、改写或覆盖字幕。
- 遇到重复或裁剪问题，先调整时间点、裁切区域或换曝光视频。
- 连续三次仍无法得到“完整、稳定、无重复”的原生字幕时，停止并让用户决定，不得暗中等价替换。

## 4. 原生字幕重复的来源

常见重复：

- 主画面本身带底部字幕，字幕条又选了同一句。
- 两个时间点落在同一个字幕段内。
- 字幕切换瞬间同时保留上一句和下一句。
- 两行字幕在同一个裁切带里重叠。
- 画面静态标题与底部字幕使用同一句话。

处理顺序：

1. 用 OCR 时间轴找到每个字幕段的中点。
2. 主画面优先选无底部字幕的帧；若没有，则主画面与字幕条不得使用同句。
3. 同一字幕段只允许选一个时间点。
4. 相邻时间点至少间隔一个完整字幕切换，通常 `>= 0.8 秒`。
5. 两行重叠时缩窄 `band-top` / `band-bottom` 或换视频，不要盲目增加字幕条高度。
6. 最后必须 OCR 回读成品，确认同一句没有重复出现。

## 5. 草稿恢复与重新上传

- 登录页、发布页使用 `markHandoff()` 保留。
- 已提交结果页使用 `markDeliverable()` 保留。
- 重新打开发布页出现“上次未发布内容，是否继续编辑”时：
  - 要继续旧稿，选择“继续编辑”。
  - 要用新素材，选择“放弃”，再打开全新上传页。
- “清空并重新上传”可能处于异步加载状态，AX 点击不一定立即生效。不要反复点击造成多个弹窗。
- 推荐用新标签页打开上传页，选择“放弃”旧草稿，再上传最终图片；确认新稿上传成功后再关闭旧标签页。
- 富文本编辑框重写时先 `Control+A`、`Backspace`，再填入新正文，避免旧文案拼接。

## 6. 定时发布的时间规则

- 抖音定时发布要求至少晚于当前时间 `2 小时`，且不超过 `14 天`。
- 用户给出的时间可能不满足限制。必须先计算 `minimum_allowed_at`。
- 平台输入框会在提交时自动调整时间。填写后必须回读输入框的最终值。
- 如果平台调整了时间，不得默认为用户接受。展示：
  - 用户请求时间
  - 平台最早允许时间
  - 实际回读时间
- 只有用户确认调整后的时间，才能提交。
- 状态文件记录 `schedule.requested_at`、`schedule.minimum_allowed_at`、`schedule.actual_at`、`schedule.adjustment_reason`。
- 示例：18:43 请求 20:30，平台最早为 20:45；必须让用户确认 20:45，不能悄悄发布。

## 7. 删除作品

- 删除前必须让用户明确说明删除范围，例如“当前定时稿”或“全部历史作品”。
- 先统计作品数量，再执行。
- 每次只删除当前页面确认可见的一条，等待列表刷新后再删下一条。
- 批量删除脚本不能依赖 DOM 立刻刷新；首选“删除一条 → 刷新 → 再删一条”。
- 删除后重新加载内容管理页，确认作品数量为 0 或符合用户要求。

## 8. 发布前最终摘要必须包含

- 热点事件原文和发布时间
- `source.role`（曝光/评论/官方）
- 用户选定的叙事主线
- 明确排除的结果事实
- 图片中实际出现的字幕顺序
- 标题、正文首段
- 背景音乐
- 用户请求时间、平台最早允许时间、最终定时时间
- 可见范围和保存权限

摘要中任一项不满足用户要求，不得点击最终发布。
## 9. 混合原始图文格式

用户要求“封面 + 事件说明 + 原始图片”时，默认使用 5 张图：

1. 封面：使用事件原始截图或原始视频画面，选择冲突最强、最容易识别事件的画面，叠加事件名称。封面不得用纯白底文字卡。
2. 事件说明：白底黑字，完整写清时间、人物、事件经过、争议点和必要回应。
3. 事件图 1：来自主曝光来源。
4. 事件图 2：来自主曝光来源的另一个画面或信息页。
5. 事件图 3：来自另一个公开来源，避免整组图片都来自同一条视频。

抖音正文只写话题标签，不再重复事件说明。

图片组合必须同时满足：

- 原始图片不重绘、不伪造。
- 同一事件至少组合两个公开来源。
- 原始图片可以裁切到 3:4，但不得改变事件内容。
- 封面文字只做事件名称和必要标识，不能把猜测写成事实。
- 事件说明负责交代完整经过，原始图片负责提供证据和现场感。

## 10. Codex 会话与工具调用故障

- 错误 `No tool output found for tool call call_...` 表示会话历史里存在悬空工具调用，不是素材损坏。继续在同一线程回复“继续”或切换模型供应商都不能修复，因为后续请求仍携带不完整消息链。
- 出现该错误后，以 `workflow-state.json`、发布计划和磁盘产物为准，fork 或新开干净线程继续；详细恢复步骤见 [codex-runtime-recovery.md](codex-runtime-recovery.md)。
- 成品图片 QA 逐张读取并确认每次工具结果返回，不要在一次工具批次里并发提交多张 `view_image`。
- 点击没有效果时先检查可见性、可用性、必填项和当前 URL；排除阻塞后再用一次 `force: true`，不要盲目连点。

## 11. 浏览器与抖音站内热点

- 浏览器必须优先使用 Codex 内置浏览器 `iab`；外部 Chrome、Edge 或系统浏览器不得作为静默回退。浏览器服务不可用时停止并说明阻塞。
- 热点扫描必须包含抖音站内证据：官方热点榜、抖音热榜、创作者中心热点或站内搜索及相关搜索。
- 官方热榜不等于抖音全部热点。品牌、产品、功能、消费服务等话题可能先出现在站内搜索；只查热榜会漏掉“荣耀魔法画报”这类搜索热点。详细流程见 [douyin-topic-discovery.md](douyin-topic-discovery.md)。
- 站内热度只证明“有人看”，不能替代事实核验；发布前仍须使用权威来源确认当事方回应和事件边界。
